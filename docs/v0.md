# v0 contract and implementation boundary

Tracks [issue #1](https://github.com/jinwon-int/danso/issues/1). Danso owns
the headless loop. It neither embeds nor ports Piri's TypeScript runtime.

## Acceptance mapping

| Contract | Implementation and evidence |
| --- | --- |
| Four tools only | `read`, `bash`, `edit`, `write`; exact surface assertion and real tool round trip |
| AGENTS + skills | Global and explicitly trusted project discovery; bounded progressive disclosure |
| Pi JSONL v3 | User, assistant, toolCall, toolResult round trip against Piri SessionManager |
| Print contract | JSONL default; `-p` final text; stable exits; both usage prefixes on stderr |
| Model paths | Anthropic Messages, OpenAI Responses and Z.AI GLM Chat Completions; local mock tested, live calls pending operator authorization. See [providers](providers.md). |

## Run

Linux 5.3+ with procfs/pidfds and Bash are required; Rust 1.98.1 is needed only
for building. Bubblewrap is optional via `--sandbox bubblewrap`. There is one
Rust harness binary; no Node/npm runtime. Node is used only for optional Piri
interoperability verification. This is not a fleet deployment or replacement.

```sh
cargo build --release --locked
mkdir -p "$HOME/.danso/sessions"
# Supply ANTHROPIC_API_KEY using your existing credential mechanism.
target/release/danso --cwd /path/to/repo \
  --session "$HOME/.danso/sessions/task.jsonl" \
  --model YOUR_ANTHROPIC_MODEL --trust-project -p 'Read and explain this repo'
```

The same session path resumes an existing linear conversation and adds the new
prompt. Session parents must already exist. Sessions must be outside the
writable workspace and are created mode 0600 with exclusive advisory locking.
Select `--provider openai` or `--provider glm` for GPT/GLM; see
[credentials, API bases and reasoning support](providers.md).
No credential is copied from another harness. OAuth/plan credentials and
provider failover are outside this first v0 implementation.

`DANSO_ANTHROPIC_BASE_URL` optionally selects an Anthropic-compatible endpoint;
HTTPS is required except literal loopback HTTP for tests. The operator must
trust any configured endpoint to receive the supplied key. Redirects are
disabled. Neither provider error bodies nor the key are printed.

## Context and trust subset

There is no persistent trust database. `--trust-project` authorizes project
context for this invocation; without it only global context is discovered.
This flag controls instruction loading, not workspace tool access.

- Global AGENTS: `~/.pi/agent/AGENTS.md`.
- Project AGENTS: filesystem-root-to-cwd `AGENTS.md` files, in that order.
- Global skills: `~/.pi/agent/skills`, then `~/.agents/skills`.
- Project skills: cwd `.pi/skills`, then `.agents/skills` from cwd through git
  root, or filesystem root outside a repository.
- `SKILL.md` recursively; root Markdown skills in Pi directories; nested
  frontmatter Markdown in grouping directories. Root Markdown other than
  `SKILL.md` in `.agents/skills` is ignored. Directory symlink cycles terminate.
- Names and descriptions enter the prompt, full bodies load through `read`.
  Duplicate names warn and keep the first. Hidden or invalid metadata is omitted.
- Canonical duplicate AGENTS paths fail, and wrapper bootstrap environment
  variables fail before any request. This detects the supported injection
  paths, not arbitrary duplicate prose inside a user's prompt.

Documented exclusions from current Piri: AGENTS.override/CLAUDE/case aliases,
nested linked-worktree shadow handling, packages/settings/CLI skill additions,
`/skill` commands and skill scripts/assets outside the workspace. Only discovered
external instruction files are mounted read-only; a skill's whole parent tree
is not exposed. No claim of complete Pi discovery or trust compatibility.

## Isolation and budgets

Host execution is the CLI default and uses current-user filesystem/network
permissions. Its supervisor reaps descendants; it does not isolate host files.
`--sandbox bubblewrap` explicitly selects the original PID/mount/network
boundary with read-only system paths, a writable workspace and private /tmp.
Both modes clear the worker environment and require preflight before model
requests. Backend failure never silently falls back. See [execution modes](execution.md)
for migration, permission and lifecycle limits.

In bubblewrap mode the workspace is writable, including `.git`. Keep credentials, host sockets,
and hardlinks to sensitive host files out of it; the sandbox does not make
already-exposed workspace resources safe. System directories are mounted
read-only as a practical shell runtime. Workspace background jobs are killed
with their tool namespace, rather than becoming persistent workers.

| Budget | Limit |
| --- | --- |
| Bootstrap plus skill catalog | 64 KiB, hard fail |
| Read/write text file | 256 KiB |
| Skill traversal | Depth 32; 4096 directories/files |
| Serialized model request | 512 KiB, hard fail; byte cap, not token estimation |
| Existing session import | 16 MiB |
| Model response | 1 MiB |
| Tool stdout / stderr | 64 KiB each; tool terminated on overflow |
| Concurrent tools | 1 |
| Tool virtual address space | Host 32 GiB; bubblewrap 512 MiB (`RLIMIT_AS`, not an RSS measurement) |
| Tool file size / descriptors / CPU | Host 4 GiB / 4096 / selected wall timeout; bubblewrap 16 MiB / 128 / 30 CPU seconds |
| Tool wall time | Host 900s default, configurable 1..3600s; bubblewrap 30s default, configurable 1..300s |
| Run wall time / turns | 1800s / 48 defaults, maxima 3600s / 128 |
| Output token cap | `--max-output-tokens` 256..=131072, default 16384 (issue #69 A) |

The enclosing run wall time still wins: the host's 900-second tool default now
fits inside the default 1800-second invocation. Raise the run timeout explicitly
for a longer host development operation.

Host development tools normally use the native `HOME`. `--tool-home
/absolute/path` selects a separate absolute HOME for the child tool's
Cargo-first `PATH`, which is useful when the provider bridge gives the native
process a private HOME. It is host-only and does not change provider
authentication or context discovery; bubblewrap rejects it. The path and its
joined PATH are validated before provider construction.

Whole-harness RSS and aggregate subprocess/fork counts are not cgroup-capped;
use an outer cgroup for adversarial workloads. Quota routing and failover are
parked v0+ work; HTTP 429 ends this invocation without automatic resend.

## Optional long-task mode

Long work is opt-in with `--long-task`; the ordinary invocation keeps the
short 1800-second default and 3600-second maximum. Long mode accepts
`--timeout-seconds` through 21600 seconds (six hours) and persists immutable
task limits in the session. Its bounded defaults are 16 model requests per
stage, 1024 cumulative model requests, 10000000 reported tokens, and a
consecutive repeat limit of 3. `--task-stage-requests`, `--task-max-requests`,
`--task-max-tokens`, and `--task-repeat-limit` select lower limits when needed;
each has a documented finite range in `--help`. A deliberately larger bounded
profile is available up to 2048 requests and 25000000 reported tokens; the
defaults remain conservative and are not silently raised for six-hour runs.

Each provider request, including compaction summaries, consumes one cumulative
request slot. Token limits use provider-reported usage; an action response is
settled before its tools run, so an over-limit response stops before side
effects, while an exact reported total stops before the next provider request.
The journal records safe stage checkpoints only after every tool in a batch has
settled. A bounded SHA-256 fingerprint of each settled batch (tool name,
arguments, result status and result bytes) detects consecutive identical work;
the fingerprint and repeat count survive stages and resume. This is a
conservative progress heuristic and can require a new task after a false
positive.

`--resume-task` takes no prompt and resumes only a ready or paused checkpoint.
Omitted immutable limit flags are loaded from the creation record; explicitly
provided values must match it. A pending provider request, pending tools,
final response, torn record, failed task or completed task is fail-closed and
never retried or replayed. A new prompt may start a fresh long task only after
the previous task is terminal. `--task-status` is a read-only, provider-free
projection of the journal.

For an operator pause, send SIGUSR1 to the native process in long mode. The
CLI installs the handler before emitting a body-free stage-0 handshake and the
runtime observes it after the in-flight provider/tool work settles. It writes
`DANSO_TASK={"version":1,"state":"checkpoint"|"paused"|"completed"|"blocked","stage":N,"requests":N,"reported_tokens":N,"elapsed_seconds":N}`
to stderr only when `--task-progress` is enabled. `--task-pause-after-stage N`
provides a deterministic equivalent for tests and operators. SIGINT/SIGTERM
remain immediate cancellation; an interrupted in-flight operation is not
resumable. Persisted elapsed time measures active execution across resumes;
paused time is excluded, and the journal's 16 MiB cap remains a fail-closed
limit.

## Session and recovery

Each append is fsynced. The transcript uses Pi v3 tree entry fields, but v0
runtime resume accepts linear, text-only transcripts, including Danso custom
checkpoints described in [compaction](compaction.md).
Unknown context roles/entries, branches and native Pi compacted sessions fail closed;
they are not flattened. Existing JSONL bytes are preserved when appending.

For each tool, the loop persists the assistant call, a `custom` entry with
`customType: danso.operation.v1` and state `started`, then the tool result,
then state `settled`. These are Pi extension-state records, not model messages.
Pi opens the transcript and ignores the operation metadata in model context.

Unresolved calls, `started` without `settled`, torn JSONL, duplicate IDs, or a
concurrent writer prevent resume before any provider request or tool launch.
This deliberately sacrifices automatic liveness across an uncertain effect
window: there is no promise of exactly-once arbitrary shell side effects.
Inspect workspace effects and preserve the original journal before starting
a new session with an explicit description of what completed. No automatic
ACK, truncation repair, rollback, or replay is performed. Fully settled tools
are supplied as history, never executed again by the resume loader.

## Process contract

Default stdout is JSONL: a session header followed by newly written message
entries. It is a Danso entry stream, not Pi's full streaming-event/RPC API.
Operation metadata is persisted in the session file. `-p` / `--mode text`
prints only a successful final answer. Diagnostic and usage lines use stderr.

| Exit | Meaning |
| --- | --- |
| 0 | Completed final answer |
| 2 | CLI/config/context/session/preflight failure before provider dispatch |
| 3 | Request or run failure after provider dispatch, including turn exhaustion |
| 124 | Whole-run wall timeout |
| 129 / 130 / 143 | SIGHUP / SIGINT / SIGTERM |

After invocation (except help/version), stderr contains exactly one each of
`DANSO_USAGE=<json>` and `PIRI_USAGE=<json>`, with Piri fields `requests`,
`inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`,
`totalTokens`, `costUsd`, `models`. Count only responses in this run, not resumed
history; failed HTTP requests without response usage do not increase counts.
Cost is **unknown**, encoded as zero for Piri schema compatibility, not a claim
that the run is free. SIGKILL/OS fatal termination cannot promise telemetry.

When the CLI handles a run or configuration failure, it emits one structured
stderr line before the usage lines: `DANSO_ERROR=<json>`. Its exact fields are
`version` (currently `1`), `category` (a serialized failure category), and
`exit_code` (the process exit code). For example:

```text
DANSO_ERROR={"version":1,"category":"provider_timeout","exit_code":3}
```

The category comes from typed errors, not matching words in diagnostic text.
An existing typed category survives added error context; the structured record
does not include raw error text. Plain diagnostic lines are separate.

| Category | Meaning |
| --- | --- |
| `configuration` | CLI/config/context validation or an unclassified setup failure |
| `session` | Journal loading, persistence, or recovery validation failure |
| `sandbox` | Executor preflight failure |
| `provider` | Provider history/request validation or request/response failure |
| `provider_timeout` | A single provider request's time limit expired |
| `compaction` | Checkpoint construction or validation failure |
| `request_budget` | The shared action/checkpoint request budget was exhausted |
| `output` | An event sink returned an error |
| `runtime` | An otherwise unclassified agent-loop error |
| `run_timeout` | The whole invocation's wall timeout expired (exit 124) |
| `interrupted` | Handled SIGHUP/SIGINT/SIGTERM (exits 129/130/143) |

`provider` can occur **before** a request is attempted, for example when saved
history cannot be represented by the selected adapter. Categories are not a
one-to-one mapping to exit codes or evidence of network delivery. A provider
request timeout is distinct from `run_timeout`, the outer limit over the whole
invocation. A tool failure recorded as `toolResult.isError` can be followed by
a successful final answer; it does not itself emit a CLI error record.

When a terminal response stops at the output token cap (`stop_reason=max_tokens`
with no tool calls), the failure keeps the `provider` category and an additional
structured record names the cap and the flag that raises it (issue #69 B):

```text
DANSO_ERROR={"version":1,"category":"provider","exit_code":3}
DANSO_PROVIDER={"version":1,"reason":"max_tokens","http_status":null,"output_tokens_max":16384}
```

Successful completions and `--help`/`--version` exits emit no `DANSO_ERROR`.
SIGKILL, fatal termination, or failure to write stderr cannot promise telemetry.
This metadata does not authorize automatic retry, resend, or replay. Usage
counts successfully recorded response usage, not all attempted requests: zero
`DANSO_USAGE.requests` does not prove that no request was attempted or that no
effect occurred. Preserve the original evidence and inspect the failure before
deciding how to continue.

## Validation and fixture provenance

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
python3 scripts/test_e2e.py
```

Tests require real bubblewrap; they never silently substitute unsafe execution.
The Python suite uses a loopback fake Anthropic server and synthetic credentials,
and tests all tools, context, usage, resume, file/env/network isolation,
symlink escape, ambiguous edit, output/time caps, HTTP errors and interrupted
side effects. No real provider call is needed.

`tests/fixtures/piri-v3.jsonl` was generated using the installed Piri
`v0.84.2-piri.1` SessionManager, image
`a2a-docker-runner-piri:v0.84.2-piri.1-cf2c218`, with `scripts/piri-fixture.mjs`.
No model or user conversation was involved. Contract source was checked against
`jinwon-int/piri` commit `84859e40f1dd68c2bd85d5f3b5fbd4d951933980`:
`docs/session-format.md`, `docs/skills.md`, and `src/modes/print-mode.ts`
under `packages/coding-agent`.

To verify against your installed Piri (optional Node test tooling):

```sh
export PIRI_SESSION_MANAGER=/path/to/piri/packages/coding-agent/dist/core/session-manager.js
node scripts/piri-fixture.mjs verify tests/fixtures/piri-v3.jsonl
DANSO_TEST_SESSION_EXPORT=/tmp/danso-roundtrip.jsonl python3 scripts/test_e2e.py
node scripts/piri-fixture.mjs verify /tmp/danso-roundtrip.jsonl
```

The installed Piri successfully parsed a Danso-generated nine-message session
and built its model context. This is equivalent parse evidence, not a claim of
testing every interactive `/resume` UI or every later Piri revision.
